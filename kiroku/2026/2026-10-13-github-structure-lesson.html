GitHubで記事が消えた日

――初心者が実際にやらかした「フォルダ構造」の罠と、その直し方
2026年10月13日（火）｜記録｜GitHub入門

GitHubを使い始めて間もないころ、私は「記事の一覧が表示されない」という問題に何度もぶつかった。エラーメッセージはこうだった。

画面に表示されたエラー
記事の一覧を読み込めませんでした。
articles.json を取得できません（404）
※このページはファイルを直接開くと動きません。GitHub Pages 上で確認してください。

結論から言うと、原因は二つあった。ファイルを間違った場所に置いていたこと、そしてどこを参照しているかが食い違っていたことだ。この記録が、同じ状況でつまずいた人の手がかりになれば嬉しい。

そもそも「フォルダ構造」とは何か

GitHubのリポジトリ（ファイルを置く場所）は、パソコンのフォルダと同じ階層構造を持っている。私のサイトの場合、記事を管理する仕組みは次のようになっている。

yymm77.github.io/
  kiroku/
    index.html　　　← 記録の一覧ページ
    2026/
      articles.json　本物・ここだけ
      2026-10-13-yoro-……html　← 記事本体

ここで大事なのは、「目録ファイル（articles.json）は kiroku/2026/ の中に一つだけある」という設計だ。ところが私はこれを理解しておらず、間違った場所にも同じ名前のファイルを作ってしまった。

やらかした三つのミス

ミス① 間違った場所にarticles.jsonを作った

最初、私は kiroku/articles.json（2026/ の外）にファイルを作った。

kiroku/
  articles.json　誤・削除すべき
  2026/
    articles.json　正・これだけ残す

2か所に同名ファイルがあると、どちらが本物か分からなくなる。しかもこの二つは中身の形式も違っていた。

ミス② ファイルの中身の形式が間違っていた

項目 誤ったファイル 正しいファイル
全体の形 単独オブジェクト { } 配列 [ { }, { } ]
フィールド名 series, episode, file, source… subtitle, type, category, path…

見た目は似ていても、一覧ページが読める形式と読めない形式がある。実際のファイルを開いて確認するまで、このズレに気づかなかった。

ミス③ 削除しようとして本物を上書きした

誤ったファイルを消そうとして操作を誤り、kiroku/2026/articles.json（本物）を上書きして壊してしまった。これが「記事が見えなくなった」直接の原因だった。

このとき起きたこと
正しいarticles.json（本物）の中身が、間違った形式のものに置き換わった。 一覧ページはファイルを読めても中身を解釈できず、「記事がない」と判断した。

もう一つの問題：fetchのパス

ファイルを正しく直した後でも、まだ404エラーが出た。今度は別の原因だった。

kiroku/index.html の中に、こういうコードがある。

fetch('articles.json', { cache: 'no-cache' })

fetch（フェッチ）とは「サーバーからファイルを取ってくる」命令のことだ。問題は、このコードが「同じ階層のarticles.json」を探すという点にある。

項目 パス
fetchが探しに行く場所 kiroku/articles.json（存在しない）
ファイルが実際にある場所 kiroku/2026/articles.json

「同じ名前のファイルがある」ではなく「同じ場所を見ているか」が大事だと、この件で初めて実感した。

修正したコード：
fetch('2026/articles.json', { cache: 'no-cache' })

2026/ を付けることで「自分がいる kiroku/ の中の 2026/ フォルダを見に行け」という指示になる。これで404エラーが解消された。

この一件で学んだこと

教訓 その一
同じ名前のファイルは、一か所にだけ置く。
複数の場所に置くと、どれが本物か分からなくなる。
教訓 その二
GitHubでファイルを編集するとき、上部に表示されているパス（例：kiroku/2026/articles.json）を必ず確認してから保存する。
教訓 その三
一覧ページがファイルを「取りに行く場所」と、ファイルが「実際にある場所」が一致していないと404になる。
エラーが出たら「どこを見ているか」と「どこにあるか」を照合する。
教訓 その四
来年（2027年）になって新しいフォルダを作ったら、fetch のパスも 2027/articles.json に変える必要がある。

記録を終えて

理解してから直すより、直してから動作を確認する方が先で構わない。今回の一連の作業を通じて、「フォルダの階層」と「ファイルを参照するパス」が連動しているという感覚が、少しだけ身についた気がする。

何十回と繰り返さないと自分の知識にならない、というのが正直なところだ。それでも、同じ問題に次に当たったとき、「あの件か」と思えるようになれば上出来だと思っている。
